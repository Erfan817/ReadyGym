产品闭环

四步构成一次完整的训练，不是功能列表的堆叠。

01 对话建档聊清目标、身体资料、每周天数、单次时长与器械条件，确认后才保存
02 生成计划按档案生成整周安排，动作、组次先过代码契约校验才落库
03 跟着练逐组记录次数、时长与重量；退出后可续上未结束的训练
04 动态调整换动作先看演示与整周变化，明确确认后同步当前训练

系统结构

客户端、AI、服务端各自负责什么。

Android App

Compose 界面、ViewModel / StateFlow、Room 本地库、Coil 媒体；档案、计划版本与训练组记录都在本机

AI 网关（App 直连）

OpenAI 兼容接口，承担聊天建档、计划生成与器械拍照识别；输出经本地解析与规则校验

Spring Boot 服务

注册、训练摘要、周榜、反馈、GIF 分发、安装包下载、语音识别中转；不做 AI 中转

周边：讯飞流式语音识别（服务端持有 WebSocket 连接）· 60 个 GIF 打包进 APK、其余 227 个从服务器加载 · 蒲公英 + VPS 个人分发

四个工程取舍

更值得说明的是「为什么这么设计」，不只是「做了什么」。

AI 输出必须过契约校验

推理型模型的 JSON 输出先由 PlanContract 校验，最多两次重试，仍不合规则拒绝保存，不把无效内容写进对话历史

新手安全双重过滤

杠铃蹲/推/拉等高风险动作对新手与恢复训练者同时被动作筛选和计划提示词排除，用户要求也不放行

计划版本事务化

聊天确认换动作后，未做的动作、组次、重量立即同步，已完成的实际组记录保留；已结束的训练不会重新打开

推理模型的 token 预算

计划生成与聊天分开给预算，视觉识别另留更高额度，因为推理型模型的思考过程同样消耗 token
