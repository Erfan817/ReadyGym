# 手写 WebSocket，把语音识别做成流式

> **状态：初稿，发布前请本人核对实现细节与所有数字。**
> 本文依据 `AGENTS.md` 中已记录的机制与事故整理，不补充任何未经核实的帧格式、代码或测量结果。
> 文中「~0.3s」等数值来自项目内部记录，对外发布前建议重新实测并写明测量口径。

## 为什么要自己写一层

App 的聊天输入框支持「按住说话」。最初的链路是：优先调用系统 `SpeechRecognizer`；设备没有识别服务时才把整段录音发到服务器，由服务器转发到讯飞。整段上传的体验问题很明显——用户松手之后要等录音上传、识别、返回，中间是一段没有反馈的空白。

目标是把这段时间压下去，同时不牺牲「识别结果先回到输入框、由用户检查后再发送」这条产品约束。识别成功自动切回输入框，失败则留在语音条允许重试——这个交互不能因为是流式就绕过去。

## 第一个坑：讯飞是 WebSocket，不是 HTTP

讯飞听写接口是 `wss://iat-api.xfyun.cn/v2/iat`，握手需要 HMAC 签名。直接对它发 HTTP POST 会拿到 403。这意味着服务器不能在收到整段音频时「一次性转发」，而要在用户说话期间就维持一条连接、边收边转。

服务端最终用 `XfAsrClient.WsClient` 手写了一个 RFC6455 单连接客户端来维持这条通道。三件套 Key 只放在服务器的 systemd 环境（`READYGYM_XFYUN_*`）里，不进客户端、也不进仓库。

**取舍**：自己维护 WebSocket 连接意味着要自己处理帧、握手、异常与回收；换来的是不需要引入额外依赖，也不需要把连接生命周期交给一个不熟悉的第三方库。对单人维护的项目，这个交换是否值得可以争论，但它至少是一个能被讲清楚的取舍。

## 流式分片怎么走

0.6.0 起改成流式：按住说话时，App 每约 0.75 秒把一小片音频 POST 到服务器，服务器持有讯飞连接边收边转。

```
App  ── /api/asr/start  ──►  服务器建立讯飞 WS 连接
     ── /api/asr/stream ──►  分片转发（按住期间持续）
     ── /api/asr/finish ──►  只等收尾，返回最终转写
     ── /api/asr/abort  ──►  取消时释放连接
```

关键在 `/finish`：绝大部分识别工作已经在按住期间完成，松手后只需要收尾，所以等待时间被压缩到很短。项目内部记录实测「松手 → 出字」约 0.3 秒。

**失败回落**：链路上任何一步失败，都自动回落到整段 `POST /api/asr`。这个老接口一直保留，既给老版本 App 兼容，也给流式链路兜底。流式是优化，不能变成单点。

## 事故：8 秒上限

服务端的 `seconds` 校验曾写成 `@Max(8)`，而 App 的录音上限约 59 秒。结果是短句正常、稍长的句子全部 400，而且现象看起来像「识别服务不稳定」，不像参数校验问题。

定位路径是对比两端对录音时长的约束，发现上限不一致后对齐到 App 的实际录音上限。

**之后加的防线**：把「服务端校验上限必须与客户端录音上限一致」写成明确维护约束，和接口说明一起留在项目文档里，避免下一次改录音时长时只改一端。这类跨端常量是很容易在迭代中悄悄漂移的地方。

## 还该补的量化

以下是发布前值得补、但目前没有可靠数字的部分：

| 指标 | 口径 | 数值 |
|---|---|---|
| 松手 → 出字 | 端到端计时，区分短句 / 长句 | 待实测 |
| 流式 vs 整段的回落比例 | 按失败原因分类计数 | 待实测 |
| 分片大小与请求数 | 不同句长下的平均分片数 | 待实测 |
| WS 连接异常率 | 握手失败 / 中途断开 / 收尾超时 | 待实测 |

没有这些数字，0.3 秒就只是内部记录里的一句话；有了口径，它才是能拿出来讲的工程结果。

## 边界与没做的事

- 系统 `SpeechRecognizer` 可用时仍优先使用它，服务器链路只是兜底，不是默认路径。
- 语音只用来把用户的话转成文字；照片只在器械拍照识别那一步离开本机。
- 没有做说话人分离、没有做离线识别、没有把音频落盘。
- 这条链路解决的是「等待感」，不是识别准确率；准确率取决于上游服务，本文不对其做承诺。

## 复盘一句话

把整段上传改成流式，真正的难点不在「分片」，而在「谁持有连接」和「失败时退回哪里」。前者决定了架构，后者决定了用户会不会卡在一个转圈的界面上。
