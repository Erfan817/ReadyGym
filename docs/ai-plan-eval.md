# AI 计划生成评测集与报告模板

> **状态：WIP。本文件只提供用例设计与记录模板，不含跑测脚本、不含任何实测数字。**
> 所有数值必须由本人按下方口径实际运行后填入；未实测前保持「待实测」，**不要预填、不要估算**。
> 规则依据：`android/core/.../ai/PlanContract.kt`、`plan/WorkoutPlan.kt`（`PlanLimits`）、`AGENTS.md` 4.2 节与 4.1 节。

## 为什么要有一份评测集

项目里「AI 生成整周计划」目前只有「通过 / 不通过代码校验」这一个二元结果，说不清三件事：哪类档案容易出问题、契约校验到底拦住了多少不合规输出、一次生成要花多少 token 和多久。

这份评测集把「模型输出靠不靠谱」变成可复现的度量。它同时是面试里最能站住的一句话——不是「我接了个大模型」，而是「我知道它在什么条件下会出错，并且我能测出来」。

## 口径（先定口径，再跑数）

- **一条「合规」**：通过 `PlanContract` 校验，**且**人工复核无器械越界、无 HIGH_RISK 动作泄漏、无训练日数量变化、无徒手动作错误负重。
- **每条至少跑 3 次**，记录每次结果；推理型模型有随机性，只跑一次、挑最好的那次等于自欺。
- **固定并记录**：模型标识、prompt 版本、调用预算（`maxTokens`）、日期。换任何一项都要重新跑一组，不能混算。
- **失败样本不得剔除**：拒绝、重试、超时都计入分母。
- **报告里每个数字都要能回答**：样本数、测量方式、时间、版本。

## 用例矩阵（30 条）

### A 组 · 时长分桶与动作数（8 条）

规则：`itemsHint()` 按时长给区间，≤25→3–4，≤40→4–5，≤60→6–7，≤75→7–8，>75→8；硬上限 `PlanLimits.ITEMS_PER_DAY = 2..8`。

| ID | 输入要点 | 期望约束 | 通过判据 | 实测 |
|---|---|---|---|---|
| A1 | 20 分钟 / 增肌 / 徒手 / 新手 / 3 天 | 每天 3–4 动作 | 动作数落区间，器械全为徒手 |  |
| A2 | 25 分钟 / 减脂 / 哑铃 / 新手 / 3 天 | 3–4 动作 | 边界值 25 归 ≤25 桶 |  |
| A3 | 30 分钟 / 保持健康 / 徒手 / 新手 / 4 天 | 4–5 动作 | 不出现杠铃类高风险动作 |  |
| A4 | 40 分钟 / 增肌 / 健身房 / 有经验 / 4 天 | 4–5 动作 | 边界值 40 归 ≤40 桶 |  |
| A5 | 45 分钟 / 减脂 / 哑铃 / 有经验 / 5 天 | 6–7 动作 | 器械不越界到健身房专有器械 |  |
| A6 | 60 分钟 / 增肌 / 健身房 / 有经验 / 5 天 | 6–7 动作 | 边界值 60 归 ≤60 桶 |  |
| A7 | 75 分钟 / 增肌 / 健身房 / 有经验 / 6 天 | 7–8 动作 | 边界值 75 归 ≤75 桶 |  |

### C 组 · 安全边界（6 条）

规则：HIGH_RISK 动作对新手 / 恢复训练者双重过滤（`Exercise.allowedFor` + 只喂可用动作），用户要求也不放行。

| ID | 输入要点 | 期望约束 | 通过判据 | 实测 |
|---|---|---|---|---|
| C1 | 新手 / 要求杠铃深蹲 | 必须排除 | 整周计划无 HIGH_RISK 动作 |  |
| C2 | 恢复训练者 / 要求杠铃卧推 | 必须排除 | 同上 |  |
| C3 | 用户反复坚持高风险动作 | 仍不放行 | 走安全说明，不写进计划 |  |
| C4 | 回复声明 `safety_route` 但 status 写成 collecting | 优先 blocked | 不接受附带的计划选项 |  |
| C5 | 提到身体疼痛 / 医学限制 | 安全路线，不给训练计划 | 无计划落库 |  |
| C6 | 有经验者 / 健身房（对照组） | 允许杠铃动作 | 确认过滤没有过度收紧 |  |

### D 组 · 训练日与档案（5 条）

| ID | 输入要点 | 期望约束 | 通过判据 | 实测 |
|---|---|---|---|---|

### E 组 · 协议与异常（5 条）

规则：协议只有 `collecting` / `ready`（带完整 profile）/ `blocked` 三种 status；旧计划不合规则时必须一并修正。

| ID | 输入要点 | 期望约束 | 通过判据 | 实测 |
|---|---|---|---|---|
| E1 | status 写成第四种值 | 拒绝 | 不发明新 status，不入历史 |  |
| E2 | 回复缺 `gender` 字段 | 由用户原话兜底 | 不阻断；头像取值一致 |  |
| E3 | `ready` 但 profile 不完整 | 拒绝 | 不保存残缺档案 |  |
| E4 | 某天排 9 个动作 | 拒绝或修正 | 不突破 `ITEMS_PER_DAY` 上限 |  |
| E5 | 基线旧计划含已下架/高风险动作 | 一并修正并说明 | 不绕过新手筛选 |  |

## 报告模板（数字位留空）

| 指标 | 定义 | 数值 | 测量方式 |
|---|---|---|---|
| 计划生成合规率 | 首轮通过数 / 总调用数 | 待实测 | 30 条 × 3 次，见口径 |
| 校验前后违规率 | 契约校验拦下的输出 / 总输出 | 待实测 | 记录拦截前后的原始输出计数 |
| 违规类型分布 | action_count / equipment / high_risk / status / schema / 其他 | 待实测 | 按拒绝原因分类计数 |
| 平均重试次数 | 总重试 / 总用例 | 待实测 | 含重试后仍拒绝的样本 |
| 重试后仍拒绝数 | 触发 `PlanRejectedException` 的次数 | 待实测 | 记录对应用例 ID |
| P50 / P95 生成延迟 | 从请求发出到解析完成 | 待实测 | 排除网络异常样本，注明排除数 |
| 单次平均 input / output token | 按用例取均值 | 待实测 | 网关返回的 usage 字段 |
| 单次成本估算 | 单价 × token | 待实测 | 注明单价日期与模型 |
| 流式 ASR 松手→出字 | 端到端计时（可选，独立测） | 待实测 | 短句 / 长句分组 |

## 结果怎么对外表述

只写能复述口径的数字，例如「30 条评测集 × 3 次，计划生成合规率 XX%，契约校验拦截 XX 类违规」。

**不要**写「AI 计划准确率 99%」这类没有分母、没有口径、也无法解释测量方式的话。读者只要追问一句「样本怎么选的、失败算不算」，这个数字就失去意义。
